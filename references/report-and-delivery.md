# 细颗粒度报告与飞书交付

本 Skill 的完整产出采用“短总览、长详情、场景行动”结构：先让读者快速判断，再逐维度拆解，最后回到真实工作场景落行动。

## 文字报告结构

用户要求完整诊断、报告、复盘或沉淀时，按以下顺序输出：

1. **一句话判断**：用大白话说明主导驱动、当前状态和最重要的含义。
2. **结论表**：固定四行——“被什么驱动 → 现在的状态 → 这意味着什么 → 所以该怎么办”。每个结果尽量一句话；支撑论据只保留来源 + 短行为锚点，每行不超过 2–3 条。完整观察句、推断和限制全部放到后面的详情。
3. **驱动方向证据链**：成就、亲和、权力/影响三维分别写“倾向 → 具体证据 → 推断逻辑 → 置信度 → 替代解释/需确认”。
4. **满足状态证据链**：自主、胜任、归属三维分别写“可见状态 → 具体证据 → 推断逻辑 → 置信度 → 不能由行为证明的部分”。
5. **场景化解释**：把动机和状态翻译成“什么工作会来电、什么工作会消耗、什么条件下会失速”。每个判断都回扣真实项目、会议、文档或协作场景。
6. **具体下一步**：给 3–5 条行动，每条都必须包含场景、动作、结果指标、时间锚点、决策/协作边界和复盘触发条件。
7. **证据覆盖与缺口**：列出读取的资产、时间窗、未读取的资产、权限缺口，以及哪些结论仍需本人确认。

“总分式”不等于把结论重复几遍。总部分负责方向和优先级，分部分负责证据和推理，行动部分负责把判断变成下一次真实工作中的动作。

## 文档语气与段落节奏

默认采用“同事风格 + 咨询风格”：从业务场景出发，先亮判断，再给证据；保留“我判断”“我倾向于”“这里还不能确认”等真实边界。标题写判断，段落写细节，行动写责任与时间。每段只讲一个意思，短句做判断，长句给证据，少用空泛的“赋能、抓手、闭环、全面推进”。

结论表与详情严格分工：表格让读者在 30 秒内看懂方向；详情让读者知道证据来自哪里、推断如何成立、还有哪些替代解释；行动让读者知道下一次具体做什么。

为避免行动段落重复长篇原始观察，先从证据中归纳 2–4 个短场景名，写入 `context.action_scenes`，例如“People/HR AI 工作流自动化：端到端流程”“AI 面试客户上线：P0/P1 与自动开箱”“CSM Agent 规划：14 节点与信息回流”。短场景名只负责定位，完整证据仍放在证据链中。

## 具体下一步的写法

每条行动用下面的字段组织：

| 字段 | 要求 |
| --- | --- |
| 真实场景 | 指向证据里的具体项目、会议、文档、客户流程或协作节点 |
| 具体动作 | 用“在什么时间，对什么对象，做什么动作”来写 |
| 结果指标 | 写出交付物、时效、质量阈值、复用率、人工介入率或决策结果等可观察结果 |
| 时间锚点 | 写下一次会议、下一轮复盘、两周内、一个周期内等明确节点 |
| 决策边界 | 写清本人可决定什么、需要谁配合、谁是最终验收人 |
| 复盘触发 | 写出何时检查，若未达成下一步如何调整 |

禁止单独使用“提升影响力、加强沟通、主动协作、争取机会、做好复盘、提高能力”等空泛表达。若证据没有给出足够场景，标记为“待补场景”，并提出一个最小澄清问题，不得自行编造项目、指标或期限。

## 飞书云文档交付

当用户要求生成报告、沉淀结果或明确要求飞书文档时，产出两份互相一致的结果：

- **文字总结**：在当前对话中完整呈现总分式报告，方便快速阅读和继续讨论。
- **飞书云文档**：保存完整报告、证据链、场景化解释、具体下一步和证据边界。

创建文档时优先使用用户指定文档；用户未指定时创建新文档。使用本人授权的 `user` 身份，避免把公司机器人身份当作个人文档归属。文档标题应包含对象范围和诊断日期，正文不得写入姓名、工号、邮箱、令牌或其他不必要的身份信息。

## 关联 Geometry Blue 画板

每份完整飞书报告默认规划 4 张 Geometry Blue（蓝色波点）画板：开头 1 张总览，中段 2–3 张分别承载驱动、状态、场景或行动。用户只要摘要时可降为 1 张。四张画板表达一条连续叙事：

`主导驱动 → 当前状态 → 真实工作场景 → 下一步动作`

画板标题写结论，节点写短动作，正文保留证据细节。画板只表达结构，不把完整证据链缩成密集小字。

默认视觉系统采用参考版式：主蓝 `#375dfe`、米色底 `#fdf0e0`、深蓝文字/边框 `#1a2240`、白色信息块；大标题负责结论，蓝色重点块负责主判断，细边框负责分组，留白负责层级。总览使用左右分栏，左侧放主题与工作对象，右侧放问题和结论；驱动画板使用“维度｜典型行为｜满足线索”的证据表；状态与行动画板使用 3 张编号卡片。至少使用 3 种构图家族，保持字体、边框和间距一致。卡片文字与边缘线之间保留至少约 24 px 的视觉安全区，尤其检查最后一行文字的基线与卡片内底，确保文字不贴边、不压线。用户提供参考画板时，先导出并读取参考画板，按参考版式覆盖默认样式。

写入流程固定为：

1. 读取目标文档结构，确定标题后的首个正文资源位置；总览画板必须成为标题后的第一个块，前面不放开场段落、引用、相关链接、结论表或其他正文。再确定“驱动方向”“动机状态”“具体下一步”等对应段落之后的中段锚点。
2. 创建或复用文档中的 `<whiteboard type="blank"></whiteboard>` 资源块，记录返回的 `block_token`。
3. 按 `geometry-board` 的视觉规则生成并检查 SVG/Scene JSON。
4. 使用 `lark-cli whiteboard +update --input_format svg --as user` 写入该 `block_token`，不得只插入一张静态截图冒充可编辑画板。
5. 重新读取文档的 outline 和每个画板前后文本，确认画板主题与段落主题匹配；必要时导出预览检查溢出、重叠和文字可读性。
6. 交付时区分“文字已生成、文档已创建、画板已写入、回读已验证”四个状态。
7. 在“相关链接”区写入 Skill 仓库、报告规范、画板 Skill 和画板直达链接，使用真实超链接，不只保留裸 URL 或纯文本。

若文档或画板写入权限不足，保留完整文字报告和本地 SVG，明确说明阻塞点；不要切换到 bot 身份绕过个人权限，也不要把静态图片写入成功说成可编辑画板已完成。

## 失败与降级

- 没有足够证据：输出假设和待核实问题，保留完整结构，不用空泛建议填充。
- 没有可写的飞书文档权限：完成文字报告，保存本地画板源文件，说明未写入原因。
- 画板预览为空或延迟：先查询原生节点或导出远端 SVG，再判断是否需要重试。
- 用户只要聊天摘要：可以省略云文档和画板，但仍保留细颗粒度证据链；用户明确要求报告或沉淀时不得只交聊天摘要。
